Java Security

Why I want you thinking about security from day one

🏦 Let's Ground This in a Real Application

Picture a banking application you're building. The moment money and personal data are involved, security stops being optional — it becomes part of the architecture itself. Here's what I never want arbitrary code running inside that application to be able to do:

⚠️ What I refuse to let untrusted code do

  • Read passwords
  • Access random memory
  • Modify system files
  • Execute unauthorized operations

🛡️ How Java's Architecture Historically Approached This

I want you to know these five concepts by name — they're the foundation Java was built on to keep code from doing exactly what I listed above:

1

Bytecode Verification

Checks that bytecode is well-formed and doesn't violate JVM rules before it runs.

2

Class Loading

Controls where classes come from and how they're introduced into the JVM.

3

Access Control

Enforces visibility rules like private, public, and package boundaries.

4

Type Safety

Prevents code from treating one type of data as another to sneak past checks.

5

Memory Isolation

Keeps a program from directly reaching into arbitrary memory addresses.

🚫
Let me correct something you may run into in older material: you'll sometimes see the old SecurityManager presented as the go-to way to lock down a Java application. I'm not going to teach it to you that way, because SecurityManager and its related APIs have been deprecated for removal since Java 17. Treat it as legacy, not as the modern recommendation.
✅
Here's what I actually want you to walk away with: Java gives you runtime and language-level safety mechanisms — but real application security still comes down to you. That means authentication, authorization, secure coding practices, encryption, careful dependency management, and input validation. The language helps; it doesn't do your job for you.

Memory Management

Where your program's data actually lives while it runs

🧠 The Big Picture

Java Application
↓
JVM
↓
Stack
Heap

Every running Java application sits on top of the JVM, which splits its working memory into these two regions I'll walk you through now.

📚 The Stack

I use the Stack primarily for:

  • Method calls
  • Local variables
  • References
  • Call frames
StackDemo.java
public static void main(String[] args) {

    int age = 25;

    calculate();

}

static void calculate() {

    int number = 10;

}

Watch what I want you to notice here: main() gets its own frame holding age, and the moment calculate() is called, it gets a completely separate frame holding number. Each method call gets its own stack frame — that's the rule I want you to remember.

The Heap

Where your objects actually live

🗃️ Objects Go on the Heap

Whenever I write code like this, I'm asking the JVM to allocate memory on the heap:

HeapDemo.java
Student student = new Student();

Here's exactly how I want you to trace what just happened:

student
↓
reference
↓
Student object
↓
Heap

student itself (the variable) lives on the Stack — it just holds a reference that points to the actual object sitting on the Heap.

Garbage Collection

How Java cleans up after you

🧹 Think About Your Room

Here's the analogy I want stuck in your head every time you hear "garbage collection." Imagine your room. Over time, you buy things:

📖 Book
💻 Laptop
🎒 Bag
🍶 Bottle

Eventually, you throw away things you don't need anymore. And periodically, someone cleans the room — you don't have to schedule it item-by-item, it just happens. That's the basic idea behind Garbage Collection.

💻 Seeing It in Code

GarbageDemo.java
public class GarbageDemo {

    public static void main(String[] args) {

        Student student = new Student();

        student = null;

    }
}

class Student {
}

The moment I write student = null;, I've removed the only reference pointing to that Student object on the heap. That object may now become eligible for garbage collection.

🚫
Here's a phrase I want you to stop using: "Garbage collection immediately deletes the object." That's not accurate, and I don't want you thinking about it that way.
✅
The correct way I want you to say it: the object becomes eligible for garbage collection — the JVM decides when and how the actual collection happens. Eligibility is not the same as deletion.

Constants

Values I never want changed after they're set

🔒 Using final

Whenever I have a value that should never change once it's assigned, I mark it final:

Constants.java
final double PI = 3.14159;

If I then try this:

Constants.java
PI = 4.5;
ResultCompilation error — I'm not allowed to reassign a final variable.
💡
An industry convention I want you adopting right now: name your constants in UPPER_SNAKE_CASE, like final int MAX_RETRY_COUNT = 3;. It's not required by the compiler, but every codebase you join will expect it.

⚠️ A Distinction I Always Test You On

CharVsString.java
char grade = 'A';
String name = "Manish";

char

A single character, always written with single quotes: 'A'. It's one of the 8 primitives.

String

A sequence of characters, always written with double quotes: "Manish". It's an object, not a primitive.
