Employee Payroll & Performance Management System

A console-based prototype for an HR technology team, built in Core Java with no external frameworks or database. Across eighteen parts, it moves from variables and control flow to classes, overloading, recursion, and a short observation on memory and JVM architecture.

Part Q — memory-notes.md
OBSERVATION

Java Memory & Garbage Collection Observation

An observation activity rather than a coding requirement — create several Employee objects, then release one.

1
2
3
4
Employee emp1 = new Employee(...);
Employee emp2 = new Employee(...);
Employee emp3 = new Employee(...);
emp2 = null;  // emp2's object becomes eligible for GC
Stack | |-- emp1 reference |-- emp2 reference |-- emp3 reference | ↓ Heap Employee Objects

Students should understand

  • Objects are created in heap memory.
  • References are used to access objects.
  • An object with no reachable reference becomes eligible for garbage collection.
  • The garbage collector manages memory automatically.
  • System.gc() is only a request/hint — it does not guarantee immediate collection.
Part R — architecture-notes.md
OBSERVATION

Java Architecture & Security Observation

Short-answer questions to complete after executing the application.

Java architecture

Java Source Code ↓ javac Compiler ↓ Bytecode (.class) ↓ JVM ↓ Machine-specific execution
To clarify — the JDK is the development kit, bundling the tools and runtime components needed to build and run Java applications; the JVM is the engine that executes the compiled bytecode.

Discussion

Identify the roles of

  • JDK
  • JRE (conceptually)
  • JVM
  • Java Compiler
  • Bytecode

Why is Java safer than languages that manipulate memory directly?

  • Strong type checking
  • Automatic memory management
  • No direct pointer arithmetic in ordinary Java programming
  • Bytecode verification
  • JVM-managed execution & runtime checks
