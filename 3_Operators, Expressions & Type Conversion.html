Arithmetic Operators

The five operators that do all your math

➗ The Five I Want You Fluent In

+

Addition

Adds two operands together.

−

Subtraction

Subtracts the right operand from the left.

×

Multiplication

Multiplies both operands.

÷

Division

Divides left by right.

%

Modulus

Gives you the remainder after division.

💻 Let's Run All Five Together

OperatorsDemo.java
public class OperatorsDemo {

    public static void main(String[] args) {

        int a = 20;
        int b = 6;

        System.out.println(a + b);
        System.out.println(a - b);
        System.out.println(a * b);
        System.out.println(a / b);
        System.out.println(a % b);

    }
}
Output26 14 120 3 2

Here's exactly how I want you to trace each line, step by step:

Step 1 — Set up the operands

a = 20 and b = 6 are both declared as int. Remember that — it matters for the division result coming up.

Step 2 — Addition & Subtraction

a + b gives 26, and a - b gives 14. Nothing surprising yet.

Step 3 — Multiplication

a * b gives 120.

Step 4 — Division (the one I always pause on)

a / b is 20 / 6, which mathematically is 3.333..., but Java prints 3.

Step 5 — Modulus

a % b gives 2 — that's the remainder left over after 6 goes into 20 three whole times.

🔍 Why Does 20 / 6 Give 3?

20 / 6
↓
Both operands are int
↓
Java performs integer division
↓
Decimal portion is dropped, not rounded
↓
Result: 3

This isn't rounding — it's truncation. Java never looks at the decimal at all when both operands are integer types.

✅
The rule I want burned into your memory: when both operands of / are integer types (int, long, etc.), the result is always an integer — the fractional part is thrown away, not rounded. If you want a decimal result, at least one operand must be a double or float, e.g. 20 / 6.0 gives 3.333....

How I compare two values and always get a boolean back

⚖️ Comparing an Age

int age = 20;

System.out.println(age < 18);

💡
A distinction I always catch beginners on: = assigns a value, == compares two values. Mixing these up is one of the most common early bugs — and every relational operator always evaluates to a boolean (true or false), never a number.

Assignment Operators

Shortcuts for "update this variable based on itself"

🧮 Watching a Score Change Step by Step

AssignmentDemo.java
int score = 10;

score += 5;
score -= 2;
score *= 2;
score /= 2;

I want you to trace score after every single line — this is exactly how I expect you to reason through compound assignment:

Step 1 — Start

int score = 10; → score is 10.

Step 2 — score += 5;

Same as score = score + 5; → 10 + 5 = 15.

Step 3 — score -= 2;

Same as score = score - 2; → 15 - 2 = 13.

Step 4 — score *= 2;

Same as score = score * 2; → 13 * 2 = 26.

Step 5 — score /= 2;

Same as score = score / 2; → 26 / 2 = 13. Final value of score is 13.

Each compound operator reads the current value of the variable, applies the operation, then writes the result straight back into the same variable.

💡
Why I use these instead of writing it out longhand: score += 5; is shorter, less error-prone, and it's what you'll see in every real codebase. Know both forms, but default to the compound version.

Increment / Decrement

The one-character shortcuts that trip up almost everyone at first

➕ Post-Increment: x++

PostIncrement.java
int x = 10;

System.out.println(x++);
System.out.println(x);
Output10 11

➕ Pre-Increment: ++y

PreIncrement.java
int y = 10;

System.out.println(++y);
Output11

🆚 Pre vs Post — Side by Side

x++ (post-increment)

Uses the current value first, then increments it afterward. That's why println(x++) printed 10 — the old value — before x became 11.

++y (pre-increment)

Increments first, then uses the new value. That's why println(++y) printed 11 directly.

x = 10
↓ evaluate x++
Value used in print
10 (old value)
Value stored in x
11 (after increment)

Post-increment hands off the old value first, then quietly updates the variable behind the scenes.

✅
The one-line rule I want you repeating back to me: post (x++) = "use it, then change it." Pre (++x) = "change it, then use it."

Ternary Operator

A compact if-else that fits in a single expression

🎯 Adult or Minor?

TernaryDemo.java
int age = 20;

String result = age >= 18 ? "Adult" : "Minor";

System.out.println(result);
OutputAdult

🔀 Reading a Ternary Like a Flowchart

condition
age >= 18 ?
true
"Adult"
false
"Minor"

Every ternary follows this exact shape: condition ? valueIfTrue : valueIfFalse — it's a full if-else compressed into one expression that produces a value.

🏦 A Real-World Example

AccountStatus.java
double balance = 5000;

String status = balance >= 1000
        ? "Account Active"
        : "Low Balance";

Since 5000 >= 1000 is true, status becomes "Account Active".

💡
When I reach for a ternary versus a full if-else: ternary shines when I'm assigning one of two simple values to a variable in a single line. The moment the logic needs more than that one decision, I switch back to a regular if-else for readability.

Type Conversion

What actually happens when data crosses between types

🗺️ The Big Picture — Two Directions

Widening
small → large
⇄
Narrowing
large → small

Widening is safe and automatic. Narrowing is risky and requires you to explicitly ask for it — I'll show you exactly why in a moment.

📈 Widening — Smaller Type → Larger Compatible Type

WideningDemo.java
int number = 100;

long result = number;

System.out.println(result);
Output100
int number = 100
↓ assigned directly, no cast
long result = 100

long can hold every value an int can, and more — so the compiler lets this happen automatically. No explicit cast required.

📉 Narrowing — Larger Type → Smaller Type

NarrowingDemo.java
double price = 99.99;

int roundedPrice = (int) price;

System.out.println(roundedPrice);
Output99

Here's the step-by-step I want you tracing every time you see a narrowing cast:

Step 1 — Start with the larger type

double price = 99.99; — this can hold decimals, and int cannot.

Step 2 — Explicitly cast with (int)

Because this move can lose data, Java forces you to write (int) — it will not do this silently.

Step 3 — The decimal is dropped, not rounded

99.99 truncates down to 99 — the .99 is simply discarded.

double price = 99.99
↓ (int) — explicit cast required
int roundedPrice = 99
↓
0.99 permanently lost
🚫
Don't say "narrowing rounds the number." It doesn't. (int) 99.99 gives 99, not 100 — the fractional part is truncated, exactly like integer division earlier this hour.
✅
What I want you to walk away with: widening happens automatically because no data can be lost. Narrowing always needs an explicit cast, like (int), because it can lose data — and once that data is gone, it's gone. Explicit casting can cause data loss, so use it deliberately.
