22

if

The simplest decision your program can make

🗳️ Eligible to Vote?

IfDemo.java
int age = 20;

if (age >= 18) {
    System.out.println("Eligible to vote");
}
OutputEligible to vote

🔀 Reading It as a Flowchart

age >= 18 ?
true
Print "Eligible to vote"
false
Skip the block entirely

A plain if has no fallback — when the condition is false, the block is simply skipped and the program moves on.

💡
What I want you to notice: the condition inside ( ) must evaluate to a boolean. The code inside { } only runs when that condition is true.
23

if-else

Giving every condition a fallback path

📝 Pass or Fail

IfElseDemo.java
int marks = 75;

if (marks >= 40) {
    System.out.println("Pass");
} else {
    System.out.println("Fail");
}
OutputPass

🔀 Now There's Always a Path Taken

marks >= 40 ?
true
"Pass"
false
"Fail"

Unlike a plain if, one of these two branches will always execute — there's no "skip entirely" outcome anymore.

24

else-if Ladder

Chaining multiple conditions in order of priority

🎓 Grading a Score

GradeDemo.java
int marks = 85;

if (marks >= 90) {

    System.out.println("A+");

} else if (marks >= 80) {

    System.out.println("A");

} else if (marks >= 70) {

    System.out.println("B");

} else if (marks >= 40) {

    System.out.println("C");

} else {

    System.out.println("Fail");
}
OutputA

🪜 Tracing the Ladder Top to Bottom

marks >= 90 ?
false → next
↓
marks >= 80 ?
TRUE → "A"

Java checks each condition top to bottom and stops at the very first one that's true. Since 85 fails the first check (>= 90) but passes the second (>= 80), it prints "A" and never even looks at the remaining branches.

✅
The order matters — always. That's why I write these ladders from the highest threshold down to the lowest. If I'd written marks >= 40 first, every passing score would incorrectly print "C" before Java ever reached the higher checks.
25

Nested if

An if living inside another if — for conditions that depend on each other

🚗 Can They Drive?

NestedIfDemo.java
int age = 25;
boolean hasLicense = true;

if (age >= 18) {

    if (hasLicense) {
        System.out.println("Can drive");
    }

}
OutputCan drive

🔀 Two Gates, Not One

age >= 18 ?
true
hasLicense ?
true
"Can drive"
false
nothing printed
false
outer block skipped entirely

The inner if only ever gets evaluated once the outer condition has already passed — you have to clear both gates for the message to print.

💡
When I reach for nesting versus &&: if (age >= 18 && hasLicense) would give the exact same result here in one line. I nest when the inner condition should only be evaluated — or needs different handling — after the outer one passes; otherwise I combine with logical operators for readability.
26

for Loop

Use this when I already know how many times I want to repeat something

🔁 Printing "Java" Five Times

ForDemo.java
for (int i = 1; i <= 5; i++) {

    System.out.println("Java");

}
OutputJava Java Java Java Java

🧩 The Three Parts, One at a Time

int i = 1
Initialization — runs exactly once, before the loop starts.
i <= 5
Condition — checked before every single iteration; the loop keeps going while this is true.
i++
Update — runs after every iteration, right before the condition is checked again.

Here's the step-by-step trace I want you able to redo on a whiteboard:

Step 1 — Initialize

i = 1. This happens once, only at the very beginning.

Step 2 — Check the condition

i <= 5 → 1 <= 5 is true, so the body runs and prints "Java".

Step 3 — Update

i++ makes i become 2.

Step 4 — Repeat until false

This cycle — check, run, update — keeps repeating. Once i becomes 6, i <= 5 is false, and the loop stops.

i <= 5 ?
↓ true
print "Java", then i++
↻ back to condition check
false → exit loop

This check → run → update → recheck cycle is the shape of every for loop you'll ever write.

27

Real-Life Loop Example

Seeing a for loop do something practical

🧾 Processing a Batch of Bills

BillProcessor.java
for (int bill = 1; bill <= 5; bill++) {

    System.out.println("Processing bill " + bill);

}
OutputProcessing bill 1 Processing bill 2 Processing bill 3 Processing bill 4 Processing bill 5

Notice this is the exact same three-part structure as Module 26 — I've just renamed i to bill and concatenated it into the message. This is the pattern I want you recognizing instantly: "repeat this action, n times, and use the counter each time."

✅
Where this shows up in real applications: processing a batch of invoices, sending a set of notifications, generating report rows — any time you have a fixed, countable set of work items, a for loop like this is exactly the right tool.

while Loop

Use this when the number of iterations depends on a condition, not a fixed count

🔢 Counting Up to 5

WhileDemo.java
int count = 1;

while (count <= 5) {

    System.out.println(count);

    count++;
}

🆚 for vs while — When I Reach for Each

for

I know the exact number of repetitions upfront — "do this 5 times," "loop through these 20 items."

while

The number of repetitions depends on something that can change unpredictably — "keep reading input until the user quits," "keep retrying until the connection succeeds."

🚫
The mistake that creates an infinite loop: forgetting count++; inside the body. If count never changes, count <= 5 stays true forever and the loop never exits. Always double-check that a while loop has a way to eventually make its condition false.
29

do-while

The loop that always runs its body at least once

1️⃣ The Important Difference

I want this sentence memorized word for word: do-while executes at least once — even if the condition is false from the very start.

DoWhileDemo.java
int count = 10;

do {

    System.out.println("Executed");

    count++;

} while (count < 5);
OutputExecuted

🔍 Why "Executed" Prints Even Though the Condition Is False

Step 1 — The body runs first, no check yet

count = 10. Java enters the do block before ever looking at the condition, so "Executed" prints immediately.

Step 2 — count increments

count++; makes count become 11.

Step 3 — Now the condition is finally checked

count < 5 → 11 < 5 is false, so the loop exits. It never runs a second time.

Run the body
↓ THEN check
count < 5 ? (false)
↓
exit — body ran exactly once

Compare this to a regular while, which checks before running the body at all — if the condition had started false there, the body would never run even a single time.

✅
When I actually use do-while: anytime the task must happen at least once no matter what — like showing a menu to a user before asking whether they want to see it again, or making at least one connection attempt before checking if it succeeded.
30

switch

A cleaner way to branch across many possible values of one variable

📅 Traditional switch

SwitchDemo.java
int day = 2;

switch (day) {

    case 1:
        System.out.println("Monday");
        break;

    case 2:
        System.out.println("Tuesday");
        break;

    case 3:
        System.out.println("Wednesday");
        break;

    default:
        System.out.println("Invalid day");
}
OutputTuesday
case 1
"Monday"
case 2 ✓
"Tuesday"
case 3
"Wednesday"
default
"Invalid day"

Java jumps straight to the matching case — no top-to-bottom checking like an else-if ladder. day == 2 matches the second case directly.

⚠️ Why break Matters

🚫
Forget a break and Java keeps going. Without it, execution "falls through" into the next case's code too, running statements you didn't intend to run. This is one of the most common traditional-switch bugs — always pair each case with a break unless falling through is deliberate.

✨ Modern switch Expressions

Now let me show you the syntax I actually want you writing in new code:

ModernSwitchDemo.java
int day = 2;

switch (day) {

    case 1 -> System.out.println("Monday");
    case 2 -> System.out.println("Tuesday");
    case 3 -> System.out.println("Wednesday");
    default -> System.out.println("Invalid day");

}
OutputTuesday

🆚 Old vs New, Side by Side

AspectTraditional switchModern switch (->)
Syntaxcase 1: ... break;case 1 -> ...
Fall-through riskYes — forgetting break is a real bugNo — each arrow case is self-contained
Can be an expressionNo (statement only)Yes — can directly produce/return a value
VerbosityMore lines, more punctuationShorter, more readable
✅
Why this matters going forward: switch expressions and pattern matching are an important part of contemporary Java — this is where the language's evolution is heading, and it's what you'll increasingly see in modern, actively maintained codebases. Learn the traditional form so you can read legacy code, but default to the arrow syntax in anything new you write.
