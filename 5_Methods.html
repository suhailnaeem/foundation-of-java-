Why Methods?

The problem methods exist to solve

🛒 Picture an E-Commerce Application

Think about everything a checkout flow has to do. If I tried to cram all of it directly inside main(), I'd end up with one enormous, unreadable block of code. Instead, I break the work into named, focused pieces:

calculateTotal()— add up everything in the cart
calculateDiscount()— apply any coupon or promotional pricing
validateUser()— confirm the customer is logged in and legitimate
sendEmail()— notify the customer their order went through
processPayment()— actually charge the card
Everything crammed into main()
↓ instead, I do this
Separate functionality into methods
✅
The core habit I want you building starting today: instead of writing everything inside main(), separate functionality into methods. Each method should do one clearly named thing — that alone makes your code easier to read, easier to test, and easier to reuse.

Basic Method

The simplest possible method — no inputs, no output

👋 A Welcome Message

MethodDemo.java
public class MethodDemo {

    static void greet() {

        System.out.println("Welcome to Java Training");

    }

    public static void main(String[] args) {

        greet();

    }
}
OutputWelcome to Java Training

Here's how I want you to trace execution the first time you see a method call:

main() starts running
↓ hits the line greet();
control jumps into greet()
↓ prints the message
control returns back to main()

Calling greet(); pauses main(), runs everything inside greet(), then hands control right back to where it left off in main().

💡
Why static and why void here: static lets main() call greet() directly without creating an object first. void means this method doesn't hand any value back — it just performs an action.

Method with Parameters

Letting the caller feed information into the method

🎓 Greeting Different Students

MethodDemo.java
public class MethodDemo {

    static void greetStudent(String name) {

        System.out.println("Welcome " + name);

    }

    public static void main(String[] args) {

        greetStudent("Rahul");
        greetStudent("Priya");

    }
}
OutputWelcome Rahul Welcome Priya

I want you to notice exactly what changes between the two calls:

Step 1 — First call

greetStudent("Rahul") — the string "Rahul" is copied into the parameter name for this one call.

Step 2 — Method runs with that value

Inside the method, name is "Rahul", so it prints "Welcome Rahul".

Step 3 — Second call, brand new value

greetStudent("Priya") runs the exact same method body again, but this time name holds "Priya".

✅
The mental model I want you keeping: a parameter is just a placeholder variable that gets filled in fresh with whatever value the caller passes in — same method body, different data, every single call.

Method Returning a Value

Getting a result back out of a method, not just an action

➕ A Simple Calculator

Calculator.java
public class Calculator {

    static int add(int a, int b) {

        return a + b;

    }

    public static void main(String[] args) {

        int result = add(10, 20);

        System.out.println(result);

    }
}
Output30
add(10, 20) is called
↓ a = 10, b = 20
return a + b executes
↓ hands 30 back to the caller
int result = 30

Unlike greet(), this method's return type is int, not void — so it must use return to hand a value back, and that value can be stored in a variable at the call site.

💡
void vs a real return type: if a method says void, it performs an action and gives nothing back — you can't assign its call to a variable. If it declares a type like int, it must return a value of that exact type on every possible path through the method.

Method Overloading

Same name, different parameter list

🧮 Three Versions of add()

Calculator.java
public class Calculator {

    static int add(int a, int b) {

        return a + b;

    }

    static int add(int a, int b, int c) {

        return a + b + c;

    }

    static double add(double a, double b) {

        return a + b;

    }

    public static void main(String[] args) {

        System.out.println(add(10, 20));

        System.out.println(add(10, 20, 30));

        System.out.println(add(10.5, 20.5));

    }
}
Output30 60 31.0

Java picks which add() to run purely by matching the arguments you passed against each version's parameter list:

CallArguments passedVersion matchedResult
add(10, 20)two intsadd(int a, int b)30
add(10, 20, 30)three intsadd(int a, int b, int c)60
add(10.5, 20.5)two doublesadd(double a, double b)31.0

This is called method overloading — the same method name, add, reused across multiple versions that differ in the number or type of their parameters.

🎯 Important Interview Point

⚠️ This is NOT method overloading

int add(int a)
double add(int a)

Both methods here have the exact same name and the exact same parameter list — (int a). Only the return type is different, and that alone is not enough. This won't even compile: Java would have no way to decide which one you meant when you call add(5), since it can't tell them apart by looking at the call itself.

🚫
Remember for interviews and exams: changing only the return type is insufficient for overloading. Overloading is determined entirely by the parameter list — the number of parameters, their types, or their order. The return type is never part of that decision.
